# 后台主题方案

> 说明：本文档用于约定后台 GUI 的主题设计、扩展方式与落地边界。本文档需与 `布局.md` 配套阅读：布局文档定义页面骨架，主题文档定义骨架与组件的颜色语义。

---

## 1. 目标与范围

本方案的目标不是单纯“换一个按钮主色”，而是建立一套可扩展、可维护、可逐步落地的后台主题机制。

当前主题方案需要同时满足以下目标：

1. 后续允许继续增加不同主题家族；
2. 新增主题时必须按统一规范补充，而不是页面各自随意定义；
3. 尽量复用 Element Plus 的主题能力，不把系统设计得过重；
4. 让主题方案既能支撑简单主色切换，也能支撑完整风格主题。

适用范围：

1. `/policy/**` 后台主布局页面；
3. Header / Aside / Main / Footer；
4. Element Plus 组件；
5. 项目自定义壳层样式。

---

## 2. 设计原则

### 2.1 布局与主题分离

- `布局.md` 负责定义页面骨架与区域结构；
- 本文档负责定义颜色语义、主题类型与扩展规则；
- 不允许在主题方案中反向改变布局骨架。

### 2.2 主题使用语义 token，不直接绑定业务页面

主题只定义：

- 页面背景
- 面板背景
- 文字颜色
- 边框颜色
- 主强调色
- hover / active 状态

不直接定义：

- 某个具体业务页面标题颜色
- 某个单独模块的特殊按钮色
- 某个页面专属卡片样式

### 2.3 暗色模式主色应比浅色模式略亮

在深色背景上，与浅色模式完全相同的主色会显得沉暗、视觉对比度不足。因此每个主题在定义 `dark` 模式的 `primary` 时，应将颜色的亮度（Lightness）提高约 5–10%。

示例：
- `light.primary: "#409eff"` → `dark.primary: "#3d8bfd"`（略亮）
- `light.primary: "#07c160"` → `dark.primary: "#1aad5b"`（同理）

这条规则同样适用于 `systemShell`（系统基础壳层）中的 `primary` 兜底色。

> 简单判断：如果在深色背景上，按钮或链接视觉上看起来"沉进去了"，就需要提亮 dark.primary。

### 2.4 暗色模式下的文字对比度

暗色模式的 `pageBg` 通常接近纯黑（如 `#0a0a0a`），在此背景上：

- **描述性文字、说明段落**：不要直接使用 `var(--theme-muted-text)`（灰色），与近黑背景的对比度往往低于 WCAG AA 标准（4.5:1）。
- **推荐做法**：使用 `var(--theme-text-color)` 配合 `opacity: 0.65`，保持可读性的同时兼顾视觉层次。

```css
/* 不推荐（深色模式下对比度可能不足） */
color: var(--theme-muted-text);

/* 推荐 */
color: var(--theme-text-color);
opacity: 0.65;
```

`mutedText` 可继续用于**浅色模式**或**表格、卡片内的次要标签**（背景是 `surfaceBg` 而非 `pageBg`），但不应用于在 `pageBg` 上独立展示的段落级文字。

### 2.5 尽量轻量，优先复用 Element Plus

- 能交给 Element Plus `primary` 推导的部分，优先交给框架；
- 仅对后台壳层补少量必要变量；
- 不追求一次性建立庞大的设计系统。

### 2.4 前期支持双形态主题，后期统一归一化消费

主题允许两种定义方式：

1. **基础主题**：只提供主色；
2. **风格主题**：提供一揽子壳层色板。

但无论哪种形式，系统内部最终都必须归一化为统一的主题 token 输出，供页面和组件消费。

---

## 3. 主题模型

主题系统采用“双轴模型”：

1. `themeFamily`：主题家族
2. `themeMode`：明暗模式

示例：

- `theme-a + light`
- `theme-a + dark`
- `theme-b + light`
- `theme-b + dark`

说明：

- `themeFamily` 用于区分不同视觉家族；
- `themeMode` 用于区分浅色 / 深色；
- 不再把整个主题系统简单等价为只有 `light / dark` 两个值。

---

## 4. 主题类型

### 4.1 基础主题

基础主题用于“快速换主色”，适合品牌色、强调色变化，不强调整体壳层气质大幅变化。

特点：

1. 定义简单；
2. 主要依赖 Element Plus 主色能力；
3. 页面背景、文字层次、边框层次主要沿用系统基础壳层预设。

适合场景：

- 品牌主色切换
- 强调色切换
- 在不改变整体壳层气质前提下扩展主题

### 4.2 风格主题

风格主题用于“整体气质变化”，适合 IDE、编辑器、工具台等强风格主题。

特点：

1. 不只改变主色；
2. 会同时改变背景、面板、文字、边框、hover、active 等壳层感受；
3. 适合明显区别于默认站点风格的主题。

适合场景：

- IDE / 编辑器风格
- 工具台风格
- 壳层气质明显区别于默认站点的主题

当前实现补充：

1. 标准主题统一使用 `appearance: "standard"`；
2. Photoshop CS3 使用 `appearance: "photoshop-cs3"`；
3. 主题级特殊样式必须通过 `data-theme-appearance` 限定作用域，不允许直接污染全局 Element Plus 样式；
4. 切回标准主题时，应清理 CS3 专属 Element 变量，避免 hover、边框、按钮质感残留到其它主题。

说明：

- 基础主题与风格主题并不是“二选一”的系统路线；
- 同一个项目可以同时存在多种基础主题与多种风格主题。

---

## 5. 主题定义规范

### 5.1 所有主题都必须提供的元信息

每个主题都必须有以下基础信息：

1. `key`：内部标识，如 `theme-a`、`theme-b`
2. `name`：展示名称，如“主题 A”、“主题 B”
3. `type`：主题类型，取值为 `basic` 或 `style`
4. `modes`：支持的模式，如 `light`、`dark`
5. `description`：简要说明主题定位

### 5.2 基础主题必填字段

基础主题第一版只要求：

1. `primary`

说明：

- `primary` 作为 Element Plus 的主色来源；
- `hoverBg` / `activeBg` 等辅助状态色由主色自动推导，避免基础主题在局部模块中残留系统蓝；
- 其余壳层颜色由系统的浅色 / 深色基础预设补齐；
- 不建议把基础主题做成“半套风格主题”。

### 5.3 风格主题必填字段

风格主题至少提供以下字段：

1. `primary`
2. `pageBg`
3. `surfaceBg`
4. `asideBg`
5. `textColor`
6. `mutedText`
7. `borderColor`
8. `hoverBg`
9. `activeBg`

说明：

- 这是一套轻量但足够可用的最小壳层规范；
- 不要求第一版就拆到非常细；
- 如后续确有需要，可在此基础上继续追加 token，但必须统一升级规范，不允许页面私自扩字段。

---

## 6. 统一主题 token 输出

无论主题原始定义是基础主题还是风格主题，系统内部最终都应输出同一套语义 token。

统一输出建议至少包含：

1. `primary`
2. `pageBg`
3. `surfaceBg`
4. `asideBg`
5. `textColor`
6. `mutedText`
7. `borderColor`
8. `hoverBg`
9. `activeBg`

当前实现已扩展但仍属于壳层语义的 token：

1. `workspaceBg`：工作区 / 画布背景，主要给 CS3 这类工具台主题使用；
2. `controlBg` / `controlBgRaised` / `controlBgSunken`：控件普通、凸起、凹陷背景；
3. `headerBg` / `headerText`：顶部壳层背景与文字；
4. `asideText`：侧边菜单文字；
5. `borderLight` / `borderDark`：拟物或经典工具台主题的高光边、暗边；
6. `surfaceGradientStart` / `surfaceGradientEnd`：面板渐变；
7. `insetHighlight` / `insetShadow`：内阴影和内高光。

归一化规则：

1. **基础主题**：
   - 先按当前 `themeMode` 选择系统基础壳层预设；
   - 再将主题自己的 `primary` 注入；
   - 根据 `primary` 推导 `hoverBg` / `activeBg`，用于卡片浅底、菜单 active、局部辅助背景等模块；
   - 最终补齐完整 token。
2. **风格主题**：
   - 主题自身提供完整壳层字段；
   - 系统只做少量兜底或兼容补全。

页面和组件层不应关心一个主题原本属于哪种定义方式，只能消费归一化后的统一 token。

## 7. 与布局方案的对应关系

本文档需与 `help/布局.md` 对齐，主题落点必须与布局区域一一对应。

### 7.1 Header

- Header 作为顶部通栏，重点受 `surfaceBg`、`borderColor`、`textColor` 影响；
- 主题切换入口应预留在 Header 右侧操作区；
- 按钮、图标 hover 状态应统一使用 `hoverBg` / `activeBg` 语义。

### 7.2 Aside 左侧菜单

- Aside 是后台风格识别度最高的区域之一；
- 基础主题可以沿用基础壳层；
- 风格主题应重点定义 `asideBg`、`textColor`、`mutedText`、`hoverBg`、`activeBg`；
- 风格主题的主要识别度通常优先在 Aside 与 Header 体现出来。

### 7.3 Main 主内容区

根据 `布局.md`，主内容区遵循“背景全宽，内容限宽”原则，因此主题落地需要分两层看：

1. 外层背景层：主要使用 `pageBg`
2. 内层白色 / 面板 / 内容容器：主要使用 `surfaceBg`、`borderColor`、`textColor`

说明：

- 不建议把整个 Main 所有层次都压成一个颜色；
- 页面结构层次应由背景层与内容层共同承接；
- 大屏场景下尤其要注意背景层与内容层的分离感。

### 7.4 Footer

- Footer 仅在后台主布局中展示；
- 建议与 Header 共享同类壳层语义，避免割裂；
- 优先使用 `surfaceBg`、`borderColor`、`mutedText`。

## 8. `.env`、浏览器存储与后端职责

### 8.1 `.env` 的职责

当前项目按 Vite mode 拆分环境配置：

1. `.env`：GUI 的公共身份底座；
2. `.env.development`：本地开发环境配置；
3. `.env.production`：生产构建环境配置。

`.env` 建议只放跨环境共享的展示身份：

```env
VITE_APP_TITLE=GA Sprite Birds
VITE_COMPANY_NAME=GA Sprite Birds
VITE_APP_BUILD_VERSION=b-2026.09.07
```

`.env.development` / `.env.production` 放具体环境的 API 和默认主题：

```env
VITE_API_BASE_URL=
VITE_API_PROXY_TARGET=http://127.0.0.1:8000
VITE_API_PREFIX=
VITE_DEFAULT_THEME_FAMILY=bootstrap
VITE_DEFAULT_THEME_MODE=system
VITE_DEFAULT_LANG=zh_CN
```

生产环境示例：

```env
VITE_API_BASE_URL=
VITE_API_PREFIX=
VITE_DEFAULT_THEME_FAMILY=bootstrap
VITE_DEFAULT_THEME_MODE=system
VITE_DEFAULT_LANG=zh_CN
```

不建议放入 env 的内容：

1. 每个主题的具体颜色值；
2. 大量零散 token；
3. 页面级细节主题配置。

兼容说明：

- 历史配置 `notepadpp` 会自动映射到 `bootstrap`；
- 如果主题名写错，会回退到当前环境配置的默认主题；
- 如果默认主题也不可用，会回退到主题注册表中的第一个主题。

### 8.2 浏览器存储职责

用户实际选择的主题建议优先保存在浏览器中。

当前阶段建议至少保存：

1. `themeFamily`
2. `themeMode`

优点：

1. 实现简单；
2. 无需等待后端接口；
3. 用户刷新或重新登录后可沿用本机偏好。

### 8.3 后端职责（后续可选）

如果后续希望实现“同账号跨设备保持统一主题偏好”，可以再增加后端用户主题配置存储。

但在当前阶段：

- 后端不是主题落地的前置条件；
- 主题可先以前端本地持久化为主。

### 8.4 主题合规规则

业务页面和布局组件应遵守：

1. 背景、文字、边框、hover、active 使用 `--theme-*` 语义 token；
2. 主按钮、链接、开关、分页等优先使用 Element Plus 的 `primary` 能力；
3. 不在普通页面写死 `#409eff`、`#304156` 等具体主题色；
4. 主题设置页的预览色应从 `normalizeThemeTokens` 读取，而不是固定某个默认主题；
5. 允许在 `theme.js`、`variables.css`、以及带 `data-theme-appearance` 作用域的强风格主题样式中出现色值。

本项目现有音频工作台和主题设置页已按上述规则巡检：上传、表单、表格、进度、抽屉和菜单均通过 token 或 Element Plus 变量消费主题。

## 9. 新增主题流程

后续新增主题时，必须遵守以下流程：

1. 确定主题家族 key 与展示名称；
2. 确定主题类型：基础主题或风格主题；
3. 明确 `appearance`，标准主题使用 `standard`，强风格主题使用独立 appearance；
4. 按对应规范补齐字段；
5. 完成统一 token 归一化接入；
6. 如果需要覆盖 Element Plus 样式，必须使用 `data-theme-appearance` 作用域；
7. 校验以下页面：
   - 登录页
   - 列表页
   - 表单页
   - 弹窗
   - 表格
   - Header / Aside / Footer
8. 切换回其它主题，确认 hover、边框、按钮、分页、表格没有残留；
9. 文档登记主题用途与设计意图。

---

## 10. 禁止事项

1. 禁止在业务页面中直接写 `if theme === 'xxx'` 这类主题分支逻辑；
2. 禁止新增主题时只补一半 token，导致不同页面残留旧主题颜色；
3. 禁止页面或组件绕过语义 token 直接硬编码主题色；
4. 禁止把某个业务页面的局部视觉规则直接上升为全局主题规范；
5. 如需新增主题字段，应先更新主题规范，再统一调整实现。

---

## 11. 结论

本项目后台主题方案采用以下统一口径：

1. 主题系统采用 `themeFamily + themeMode` 双轴模型；
2. 主题支持两种形态：基础主题、风格主题；
3. 基础主题只提供主色，风格主题提供最小壳层色板；
4. 系统内部统一归一化为语义 token 供页面与组件消费；
5. `.env` 只承担默认值职责，用户实际选择优先保存在浏览器；
6. 默认主题家族由具体项目配置决定，建议通过 `.env` 提供默认值。

本方案用于约束后续主题开发，避免主题能力随着业务增长而失控、分散或与布局体系脱节。

## 12. 二次开发与主题定制指南

> 本节面向把当前项目作为后台主题框架复用的场景。目标是让新项目可以快速替换品牌色、扩展主题，同时不破坏现有主题隔离和 Element Plus 的主题原则。

### 12.1 推荐上手顺序

二次开发时建议按以下顺序处理：

1. 先确认项目名称、默认语言、默认主题；
2. 再决定是“只换主色”还是“新增完整风格主题”；
3. 最后再调整少量业务页面样式。

对应文件：

```text
.env                             跨环境展示身份底座
.env.development                 本地开发 API、默认主题
.env.production                  生产 API、默认主题
src/assets/styles/theme.js       主题注册表、token 归一化、Element Plus 变量写入
src/assets/styles/common.css     全局样式与强风格主题的作用域覆盖
src/store/modules/theme.js       主题状态、浏览器持久化、兜底逻辑
src/components/layout/*.vue      Header / Sidebar / Main / Footer 壳层消费 token
src/views/policy/audio/*.vue     音频工作台消费主题 token
```

### 12.2 只想换品牌主色

如果只是把框架换成另一个项目的品牌色，优先新增或修改一个 `basic` 主题。

建议做法：

1. 在 `themeRegistry` 中新增一个主题 key；
2. `type` 使用 `basic`；
3. `appearance` 使用 `standard`；
4. `colors.light.primary` 和 `colors.dark.primary` 分别配置浅色、暗色主色；
5. 不要额外覆盖 Header、Sidebar、表格、按钮等组件样式。

示例：

```js
brand: {
  key: "brand",
  appearance: "standard",
  nameKey: "theme.name.brand",
  type: "basic",
  modes: ["light", "dark"],
  descriptionKey: "theme.desc.brand",
  colors: {
    light: { primary: "#1677ff" },
    dark: { primary: "#4096ff" },
  },
}
```

适合场景：

1. 大多数后台管理系统；
2. 只需要品牌主色差异；
3. 不希望维护大量定制 CSS。

### 12.3 想做完整视觉风格

如果主题不只是换主色，而是要像 Photoshop CS3 一样改变整体壳层气质，就新增 `style` 主题。

新增风格主题时必须做这些事：

1. 在 `themeRegistry` 中补齐浅色、暗色两套 token；
2. 给主题设置独立 `appearance`，例如 `appearance: "my-theme"`；
3. 所有特殊 CSS 都必须写成 `:root[data-theme-appearance="my-theme"] ...`；
4. 切换回 `standard` 主题后，不应残留该主题的 hover、边框、阴影、按钮样式；
5. 如果新增 token，必须先更新本文档的 token 说明，再改代码。

不推荐做法：

1. 不要在业务页面写 `themeFamily === "xxx"` 判断；
2. 不要为了某个页面单独新增全局主题变量；
3. 不要直接覆盖 `.el-button`、`.el-table` 等全局选择器而不加主题作用域；
4. 不要把 Element Plus 组件改成完全脱离其变量体系的私有样式。

### 12.4 修改现有主题时的原则

修改现有主题时，应优先修改 token，而不是到处改 CSS。

优先级建议：

1. 能通过 `primary` 解决的，只改 `primary`；
2. 能通过 `pageBg`、`surfaceBg`、`textColor`、`borderColor` 解决的，只改 token；
3. 只有强风格主题需要特殊质感时，才在 `common.css` 中追加作用域 CSS；
4. 如果发现必须改组件内部结构，先判断它是不是布局问题，而不是主题问题。

简单判断：

1. 颜色不对，多半改 `theme.js`；
2. hover、边框、阴影残留，多半查 `common.css` 的作用域；
3. Header / Sidebar / Main 的区域颜色不对，多半查布局组件是否正确消费 token；
4. 页面宽度不舒服，多半查 `布局.md` 和 `page-container--*`，不要混到主题里处理。

### 12.5 Element Plus 主题原则

当前框架仍然以 Element Plus 为基础，主题系统不应绕开它。

必须保持：

1. 主色写入 `--el-color-primary`；
2. 背景、文字、边框尽量同步到 Element Plus 变量；
3. 暗黑模式仍通过根节点 `.dark` 与 Element Plus 暗色变量配合；
4. 标准主题不做大规模组件重绘；
5. 强风格主题允许覆盖组件质感，但必须限制在自己的 `data-theme-appearance` 下。

这样做的好处：

1. 后续升级 Element Plus 更稳；
2. 新增业务页面时不用重新适配大量组件；
3. 切换主题时不会出现半新半旧的视觉残留；
4. 新项目接入时只需要理解 token，不需要理解所有组件 CSS。

### 12.6 `.env` 配置建议

新项目复用时，建议先改这些值：

```env
VITE_APP_TITLE=Your Admin
VITE_APP_BUILD_VERSION=1.0.0
VITE_COMPANY_NAME=Your Company
```

说明：

1. `.env` 只放跨环境共享展示身份；
2. `VITE_DEFAULT_THEME_FAMILY` 放在 `.env.development` / `.env.production` 中，只决定系统默认主题；
3. 用户切换后的主题会优先保存在浏览器本地；
4. 如果主题 key 写错，会回退到默认主题；
5. 本项目无需登录模式和 Token 配置。

### 12.7 新增主题验收清单

新增或大改主题后，至少检查这些页面和状态：

1. 音频生成工作台；
2. 主题设置页；
3. 表格、上传、表单和进度状态；
4. 弹窗、抽屉、下拉菜单；
5. 开关、输入框、选择器；
6. Header、Sidebar、Footer；
9. 浅色模式与暗黑模式；
10. 从新主题切换回其它主题后，确认 hover、边框、背景、按钮样式没有残留。

如果只做品牌主色主题，通常检查 1 到 5 即可；如果做强风格主题，必须完整检查 1 到 10。

### 12.8 推荐的二次开发边界

为了让这个项目长期适合作为框架复用，建议保持以下边界：

1. 主题系统只负责视觉语义，不负责业务布局；
2. 布局系统只负责页面骨架和内容宽度，不负责品牌色；
3. 业务页面只消费 token 和页面容器类，不直接判断具体主题；
4. 登录页可以有独立视觉，但仍必须消费全局主题 token；
5. 新增主题时先走注册表和 token，最后才考虑 CSS 覆盖。

一句话原则：

> 先改 token，再改作用域 CSS；先遵守 Element Plus，再补强风格细节；先保证主题隔离，再追求视觉个性。
